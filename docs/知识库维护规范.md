# 知识库维护规范

> 最后核对：2026-10-13

本规范约束 `docs/` 下所有文档的写作、更新与删除方式，保证同一事实只有一个权威来源。

## 1. 目录职责

| 目录 | 只放什么 | 不放什么 |
|---|---|---|
| `docs/`（根） | 知识库入口 `README.md`、维护规范、学习与协作叙事 | 技术事实的唯一来源 |
| `product/` | 产品范围、稳定 ID、状态、与同类产品的能力差距 | 实现细节、测试数字 |
| `architecture/` | 当前生效的分层、契约、数据模型、边界与已知缺口 | 未落地方案、阶段进度 |
| `adr/` | 已接受的重大不可逆取舍 | 待讨论提案、临时决定 |
| `roadmap/` | 未完成或明确暂缓的能力 | 已完成能力的记录 |
| `quality/` | 自动化证据、覆盖率状态、发布门禁 | 手工感受、主观评价 |
| `platform/` | 特定运行环境的事实与可复用故障经验 | 通用架构描述 |

## 2. 事实分层与写法

- **当前事实**（`architecture/`、`product/`）：用陈述句写明「现在是什么」，不写「可能会怎样」。
- **决策**（`adr/`）：写清背景、选项、取舍理由和失效条件；已接受的 ADR 只在被取代时改动状态。
- **经验**（`platform/`）：统一使用「现象 → 根因 → 预防门禁」三段式，不写流水账。
- **路线**（`roadmap/`）：写清目标、范围、退出门禁；完成后把长期事实迁出，并删除该路线文件。

## 3. 稳定 ID 规则

- 产品功能使用 `FC-` 前缀 + 三位数字，例如 `FC-001`。
- ID 一经分配不再回收；功能取消时把状态改为「已取消」而非删除行。
- 架构文档、ADR、路线文档不单独编号，靠文件名与标题区分。

## 4. 单一权威来源

- 功能范围与状态只在[产品全量功能清单](product/产品全量功能清单.md)维护。
- 分层与端口只在[当前架构](architecture/当前架构.md)维护。
- 自动化与线上证据只在 `quality/`、`platform/` 维护。
- 其他文档需要引用时使用 Markdown 链接，不复制内容。

## 5. 文档与代码的一致性

- 改动 `app/api/`、`lib/`、`hooks/` 的对外行为后，必须同步更新对应架构文档。
- 发现文档与代码不一致时，以代码为准，并在本次提交内修正文档；不允许留下已知错误描述。
- 环境变量增删后，必须同步以下三处：`.env.example`、[配置与请求防护架构](architecture/配置与请求防护架构.md)、[部署与运行环境](platform/vercel/部署与运行环境.md)。

## 6. 链接与排版

- 站内链接使用相对路径，文件名与目标文档标题保持一致。
- 表格用于结构化对比，连续叙事用列表或段落，不混用。
- 代码块只用于协议载荷、命令和真实签名，不整段粘贴实现。

## 7. 提交前检查

- [ ] 本次改动涉及的事实已在唯一权威文档中更新
- [ ] 新增/删除文件后，`docs/README.md` 的路由表与索引同步更新
- [ ] 站内链接可点击且目标存在
- [ ] `npm run test:ci` 与 `npm run build` 通过（涉及代码改动时）
- [ ] 无真实密钥、无 `.env.local` 内容进入文档
