# 限流与可观测性收口

> 状态：未开始
>
> 完成后把长期事实迁入 `architecture/` 与 `platform/`，删除本文件。

## 1. 要解决的问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 限流不跨实例 | 进程内 `Map`，见 [ADR 0004](../adr/0004-内存滑动窗口限流的适用边界.md) | 多实例部署下防护失效 |
| 限流不覆盖读接口 | 仅 `POST /api/chat` | 会话列表与历史消息可被高频拉取 |
| `/api/debug` 无鉴权 | 返回 Supabase URL 与 key 前缀/长度 | 对外泄露部署信息 |
| 无结构化日志 | 仅 `console.error` 文本 | 线上问题无法检索与聚合 |
| 无错误上报 | 无 | 异常只能靠用户反馈发现 |
| 无告警 | 无 | 额度耗尽或上游故障无感知 |

## 2. 收口方案

### 2.1 限流

- 把计数迁移到共享存储（Vercel KV / Upstash Redis），键为 `ratelimit:{userId}:{route}`；
- 保留滑动窗口语义，但改为「固定窗口 + 剩余配额头」以降低往返成本；
- 对读接口使用更宽松的独立配额；
- 超出配额返回 `429` 并附 `Retry-After`。

### 2.2 自检接口

- 首选：直接删除 `app/api/debug/route.ts`；
- 若需保留排障能力，则改为服务端环境变量开关控制 + 必须登录，且只返回布尔值（是否存在），不返回前缀与长度。

### 2.3 可观测性

- 统一日志字段：`requestId`、`userId`（可哈希）、`route`、`status`、`durationMs`、`errorCode`；
- 引入错误上报（如 Sentry）并只上报服务端异常，正文脱敏；
- 对上游错误按状态码分类计数，便于识别是额度问题还是网络问题；
- 设置额度与错误率告警阈值。

## 3. 退出门禁

- [ ] 限流在 ≥ 2 个实例下经实测共享生效
- [ ] `/api/debug` 已删除或已鉴权脱敏
- [ ] 日志字段规范落地，能在托管平台按 `requestId` 串联一次请求
- [ ] 错误上报接入并验证一条异常可被检索到
- [ ] 告警阈值配置完成并做过一次演练
