## 1. 范围

| 能力 | 目标 | 当前状态 |
|---|---|---|
| 检索增强（RAG） | 上传 PDF / 文档后基于内容问答，回答带来源引用 | 未开始 |
| Function Calling / Tool Use | 模型可调用受控工具（计算、时间、外部查询） | 未开始 |
| 结构化输出 | 以 JSON Schema 约束输出，供下游程序消费 | 未开始 |

明确不做：多模态（图片/语音）、自训练模型。

## 2. 已具备的前置条件

- 请求链路已支持自定义 system prompt 注入（`app/api/chat/route.ts`）；
- 上游为 OpenAI 兼容接口，`tools` / `response_format` 字段可直接透传；
- 已有 Zod 校验层，可作为工具入参校验的复用基础。

## 3. 开工前必须先解决的问题

| 问题 | 说明 |
|---|---|
| 向量存储选型 | Supabase 已具备 `pgvector` 扩展能力，优先复用，避免引入第二套数据库 |
| 文件上传与解析 | 需要新的上传端点、存储桶与文本抽取流程，涉及新的安全面（文件类型、大小、隔离） |
| Token 预算 | 检索片段与工具结果都会挤占上下文，必须与现有 20 条上下文裁剪策略统一 |
| 流式协议扩展 | 工具调用会产生非 token 中间态，[ADR 0002](../adr/0002-SSE流式响应协议.md) 的精简载荷需要扩展而不是打补丁 |
| 计费与限流 | 工具调用与检索同样消耗额度，[ADR 0004](../adr/0004-内存滑动窗口限流的适用边界.md) 的替换是前置条件 |
