# 数据模型与持久化架构

> 最后核对：2026-10-13
>
> 存储只有 Supabase 一处，访问只经 `lib/supabase.ts`。本文描述表结构、读写路径与持久化约束。

## 1. 表结构

> 建表 SQL 当前未入库，以下结构由代码中的查询与写入反推，字段名与类型以线上库实际结构为准。

### `sessions`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` | 主键，默认生成；前端与 URL 中使用 |
| `user_id` | `text` | Clerk 的 `userId`（非 Supabase `auth.uid()`）；隔离依据 |
| `title` | `text`，可空 | 新建时为 `null`，首次 AI 回复后生成 |
| `updated_at` | `timestamptz` | 发送消息与切换会话时刷新，用于侧边栏排序 |
| `created_at` | `timestamptz` | 由数据库默认值维护 |

### `messages`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` | 主键；前端映射为 `msg-${id}` 作为列表 key |
| `session_id` | `uuid` | 关联 `sessions.id`；删除会话时先按此字段清理 |
| `role` | `text` | 仅 `'user'` / `'assistant'`（`system` 只存在于前端与请求体） |
| `content` | `text` | 消息正文（含中断标记） |
| `created_at` | `timestamptz` | 历史消息按此升序返回 |

## 2. 读写路径

| 操作 | 入口 | 语句要点 |
|---|---|---|
| 新建会话 | `POST /api/chat`（无 `sessionId`） | `insert({ user_id, title: null, updated_at: now })` → `select("id").single()` |
| 校验会话归属 | `POST /api/chat`（有 `sessionId`） | `select("id").eq("id", sid).eq("user_id", userId).single()`，失败抛「会话不存在或无权访问」 |
| 刷新会话时间 | 同上 | `update({ updated_at: now }).eq("id", sid).eq("user_id", userId)` |
| 存用户消息 | `routes` → `saveUserMessage` | `insert([{ session_id, role: "user", content }])`，失败抛错 |
| 存 AI 消息 | `sse-response` → `insertAssistantMessage` | `insert([{ session_id, role: "assistant", content }])` |
| 生成标题 | `tryUpdateSessionTitle` | 先 `select("title")`，为空才 `update({ title: 前 30 字 })` |
| 会话列表 | `GET /api/sessions` | `select("id, title, updated_at").eq("user_id", userId).order("updated_at", desc)` |
| 历史消息 | `GET /api/sessions/[id]/messages` | 先查 `sessions.user_id` 比对，再 `select("*").eq("session_id").order("created_at", asc)` |
| 删除会话 | `DELETE /api/sessions/[id]` | 先 `delete().eq("session_id", sid)` 清消息，再 `delete().eq("id").eq("user_id")` 删会话 |

## 3. 客户端映射

后端返回的 snake_case 字段在 `hooks/useSessions.ts` 中映射为前端 camelCase：

| 后端 | 前端 `ChatMessage` |
|---|---|
| `id` | `msg-${id}` |
| `session_id` | `sessionId` |
| `role` / `content` | 同名 |

前端不做乐观写入数据库，也不维护本地缓存副本；所有持久化真相以服务端返回为准。

## 4. 持久化约束

- **单一写入方**：所有写操作只在 Route Handler 与 `lib/session-helpers.ts` 中发生，客户端组件与 hook 不直接调用 Supabase。
- **AI 回复幂等**：`saveAiReply` 用 `savePromise ??=` 做锁、`hasSaved` 做终态标记，保证同一请求只插一条 assistant 消息。
- **删除不留孤儿**：删会话前显式清理 `messages`，不依赖数据库级联约束（当前未确认库端是否配置 `ON DELETE CASCADE`）。
- **排序依赖 `updated_at`**：会话顺序完全由该字段决定；`resolveSession` 更新失败只打日志不阻断。
- **标题只生成一次**：已有标题不再覆盖，避免用户看到标题反复跳动。

## 5. RLS 与鉴权

历史问题是 `sessions.user_id` 为 `text` 而 Supabase 原生 `auth.uid()` 返回 `uuid`，类型不匹配导致 RLS 策略报 `text = uuid`。当前策略是**放弃原生 RLS，改用 Clerk + 服务端显式校验（BFF 模式）**：

- 服务端使用 service role key，绕过 RLS；
- 每个读/写语句都显式带上 `.eq('user_id', userId)` 或先做归属比对；
- 任何越权请求在校验阶段返回 403 / 404。

## 6. 已知缺口

| 缺口 | 影响 | 建议 |
|---|---|---|
| 建表 SQL 未入库 | 无法可复现地重建环境 | 增加 `supabase/migrations/*.sql` 并纳入版本管理 |
| 无索引声明 | `messages.session_id`、`sessions.user_id` 上的查询缺少可确认的索引 | 随迁移脚本一起补充 |
| 无级联删除约束确认 | 依赖应用层清理，若绕过 API 直删会留孤儿 | 库端补 `ON DELETE CASCADE` |
| 长会话全量拉取 | 单会话消息数增长后一次返回全部 | 增加分页，见[成熟软件完整性审计](../product/成熟软件完整性审计.md)的对话体验缺口 |
| 无软删除与回收站 | 删除不可恢复 | 若产品需要再加 `deleted_at` |
