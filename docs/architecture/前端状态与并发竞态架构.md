# 前端状态与并发竞态架构

> 最后核对：2026-10-13
>
> 本文描述客户端状态拆分、竞态与闭包处理。请求协议见[请求链路与 SSE 流式契约](请求链路与SSE流式契约.md)，取消语义见 [ADR 0005](../adr/0005-取消生成与中断的数据一致性.md)。

## 1. 拆分原则

状态按「谁拥有、谁负责」拆成三个 hook，互不引用，由 `app/page.tsx` 显式装配：

| hook | 拥有 | 不拥有 |
|---|---|---|
| `useChatStream` | 消息列表、输入、加载、状态、流式读取 | 会话列表、登录态 |
| `useSessions` | 会话列表、当前会话、删除流程 | 消息内容 |
| `useDarkMode` | 主题 | 其他一切 |

拆分动机：让「网络流读取」与「会话管理」的复杂度不互相放大，并让状态更新更容易被单独测试。

## 2. `useChatStream` 的内部结构

### 2.1 响应式状态

| 状态 | 用途 |
|---|---|
| `input` | 输入框内容（受控） |
| `messages` | 消息数组，UI 的唯一渲染来源 |
| `loading` | 是否有进行中的请求（驱动发送/取消按钮切换） |
| `status` | `'idle' \| 'loading' \| 'canceled' \| 'error'`，驱动提示文案 |
| `error` | 最近一次错误文案 |
| `isStreaming` | 是否已收到首个 token（用于替换「正在思考」占位） |

### 2.2 非响应式 ref

| ref | 作用 |
|---|---|
| `abortControllerRef` | 当前请求的取消句柄 |
| `messagesEndRef` | 滚动锚点 |
| `currentAiIdRef` | 正在流式填充的 AI 消息 id |
| `isFinishRef` | 防止 `finishAiReply` 被重复执行 |
| `manualCancelRef` | 区分「用户主动取消」与「被动超时」 |
| `timeoutRef` | 客户端 120s 定时器 |
| `tokenBufferRef` | 待合并的 token 缓冲 |
| `throttledFlushRef` | 10ms 节流刷写函数 |
| `hasReceivedFirstTokenRef` | 首 token 是否已直出 |
| `messagesRef` | 消息最新快照，规避闭包捕获旧数组 |

## 3. 竞态与闭包的四处关键处理

| 场景 | 风险 | 处理 |
|---|---|---|
| 快速切换会话 | 旧会话的慢响应覆盖新会话消息 | `app/page.tsx` 的 `sessionRequestIdRef`：每次切换自增，`await` 返回后比对，不匹配直接丢弃 |
| 异步任务中读消息列表 | React 闭包捕获旧 `messages` | 用 `messagesRef.current` 作为构造请求的依据，`useEffect` 同步快照 |
| 同一回复被多次收尾 | `onComplete`、超时、取消都可能触发收尾 | `isFinishRef` 单次门 + `finishAiReply` 幂等 |
| 旧 `resetChat` 引用 | 切换会话时闭包锁死旧函数 | `finishAiReply` 用 `useCallback` 包裹并对外暴露稳定的 `resetChat` |

## 4. 状态机

```
                 handleSubmit
     idle ──────────────────────► loading
      ▲                              │
      │  流正常结束                   ├── 用户取消 ──► canceled
      └──────────────────────────────┤
                                     ├── 120s 超时 ─► error
                                     ├── 超长/重复 ─► error
                                     └── 其他异常 ──► error

     resetChat（切换/新建会话）: any ──► idle
```

约束：`loading === true` 时拒绝新的提交（`if (!text || loading) return`），保证同一时刻只有一路流。

## 5. 取消语义

- 触发方式：点击「取消」按钮、按 `Esc`（仅在 `loading` 时生效）。
- 取消时的消息处理：
  - AI 已生成内容长度 `< 10` → **整条移除**该占位气泡，避免留下无意义片段；
  - 已生成内容 `≥ 10` → 保留并在末尾追加 `[已取消生成]`；
  - 找不到目标消息 → 追加一条 `system` 角色的提示消息。
- 取消后必须 `flush()` 缓冲、清定时器、复位 `loading`/`isStreaming`，并刷新会话列表（因为服务端可能已落库部分内容）。

## 6. 流式刷新策略

| 阶段 | 行为 |
|---|---|
| 首个 token | 立即写入 state，同时 `setIsStreaming(true)`，让「思考中」尽快消失 |
| 后续 token | 累积到 `tokenBufferRef`，由 10ms 节流的 flush 合并写入 |
| 流结束 / 出错 / 取消 | 强制 `flush()`，确保结尾不丢字 |

节流窗口在代码中为 10ms；[学习日志](../learning-log.md)中提到的 50ms 为早期版本，以代码为准。

## 7. 已知缺口

| 缺口 | 影响 | 追踪 |
|---|---|---|
| 无单测覆盖竞态与节流 | 上述处理无自动化保护 | [测试与持续集成路线](../roadmap/测试与持续集成路线.md) |
| `localStorage.currentChatSessionId` 只写不读 | 刷新页面后不恢复上次会话 | [产品全量功能清单](../product/产品全量功能清单.md) FC-016 |
| 消息列表无分页 / 虚拟滚动 | 长会话一次性渲染全部节点 | 未排期 |
| 无草稿持久化 | 刷新丢失未发送内容 | 未排期 |
| 超时后不自动重试 | 用户需手动重发 | 未排期 |
| 消息 id 使用 `Date.now()` | 同一毫秒内并发可能重复 | 低概率，可换 `crypto.randomUUID()` |
