# 当前架构

> 最后核对：2026-10-13
>
> 本文描述 FlowChat 当前生效的分层、状态所有权、模块边界和已知缺口。逐文件导航见[代码目录与文件职责](代码目录与文件职责.md)。

## 1. 形态与运行时

FlowChat 是单体 Next.js（App Router）全栈应用，前后端同仓、同一次构建、同一部署单元：

- **构建**：Next.js 16 + React 19 + TypeScript（`strict`）。
- **运行**：Vercel Serverless Function 承载 Route Handler；浏览器承载所有 UI 与流式解析。
- **样式**：Tailwind CSS v4（`@tailwindcss/postcss`），深色模式用 `class` 策略挂载在 `<html>`。
- **无独立后端服务、无自建数据库、无自建模型推理**。

## 2. 分层

```
┌─────────────────────────────────────────────┐
│ 展示层  app/page.tsx、components/chat/*      │  纯渲染与事件转发
├─────────────────────────────────────────────┤
│ 交互状态层  hooks/useChatStream、useSessions │  客户端状态所有权
│            hooks/useDarkMode                 │
├─────────────────────────────────────────────┤
│ 传输层  fetch + ReadableStream 逐行解析      │  浏览器 ↔ Route Handler
├─────────────────────────────────────────────┤
│ 路由层  app/api/**/route.ts                  │  鉴权、校验、编排、SSE 出口
├─────────────────────────────────────────────┤
│ 领域服务层  lib/*.ts                         │  AI 调用、流解析、限流、持久化
├─────────────────────────────────────────────┤
│ 数据层  lib/supabase.ts（service role 单例） │  唯一数据库入口
└─────────────────────────────────────────────┘
        ↓ 外部               ↓ 外部
   SiliconFlow / 兼容 OpenAI 端点      Supabase Postgres
   Clerk（身份）                        Vercel 边缘（部署与代理）
```

依赖方向自上而下单向；`components/` 不得直接访问数据库或上游模型，必须经 Route Handler。

## 3. 状态所有权

| 状态 | 所有者 | 生命周期 | 说明 |
|---|---|---|---|
| `messages`、`input`、`loading`、`status`、`isStreaming` | `hooks/useChatStream` | 组件挂载期 | 对话的唯一客户端真相 |
| 流式读取中间量（`tokenBufferRef`、`currentAiIdRef`、`isFinishRef`、`manualCancelRef`、`hasReceivedFirstTokenRef`） | `useChatStream` 内部 ref | 单次请求 | 跨闭包、不触发渲染 |
| `abortControllerRef` | `useChatStream` | 单次请求 | 级联取消上游 |
| `sessions`、`currentSessionId`、`loadingSessions`、`loadingMessages`、`deleteConfirm` | `hooks/useSessions` | 组件挂载期 | 会话列表与当前选择 |
| `isDark` | `hooks/useDarkMode` | 组件挂载期 | 初始值读 `localStorage`/系统偏好 |
| `sidebarOpen` | `app/page.tsx` | 组件挂载期 | 仅移动端抽屉 |
| `sessionRequestIdRef` | `app/page.tsx` | 组件挂载期 | 会话切换竞态编号 |
| 会话与消息的持久真相 | Supabase `sessions` / `messages` | 永久 | 客户端状态只是缓存 |

客户端不存在全局 store（无 Redux/Zustand/Context）；跨 hook 协作靠 `app/page.tsx` 显式传递回调。

## 4. 稳定端口与边界

| 边界 | 唯一入口 | 约束 |
|---|---|---|
| 浏览器 → 服务端 | `POST /api/chat`、`GET /api/sessions`、`GET /api/sessions/[id]/messages`、`DELETE /api/sessions/[id]` | 全部要求 Clerk 会话；除 `/api/debug` 外均做归属校验 |
| 服务端 → 上游模型 | `lib/ai-service.ts#fetchAIResponse` | 唯一出网点；`Authorization: Bearer ${SILICONFLOW_API_KEY}` 只在服务端拼装 |
| 服务端 → 数据库 | `lib/supabase.ts` 导出的 `supabase` 单例 | 必须使用 service role key；不得被客户端组件 import |
| 服务端 → 浏览器 | `lib/sse-response.ts#createSSEResponse` | 唯一 SSE 出口，负责响应头与中断收尾 |
| 请求 → 上游 | `hooks/useChatStream` 的 `AbortController` → `request.signal` → 上游 `signal` | 取消必须逐级传递，不允许断链 |

## 5. 关键约束

- **同一事实不双写真相**：流式内容先在前端累积渲染，落库发生在服务端 `StreamProcessor` 的 `onComplete` / `onError`，前端不发起落库请求。
- **AI 回复落库有且仅有一次**：`saveAiReply` 用 `savePromise` 作锁 + `hasSaved` 标记，避免 `onComplete`、`onError`、取消三条路径重复插入。
- **越权防护不依赖数据库 RLS**：历史表结构的 `user_id` 与原生 `auth.uid()` 类型不匹配，因此鉴权由 Clerk + 服务端显式校验承担（BFF 模式）。
- **上下文有双上限**：前端只发最近 20 条，服务端再次 `slice(-20)` 并校验 `max(20)`。
- **服务端密钥永不下发**：`SUPABASE_SERVICE_ROLE_KEY`、`SILICONFLOW_API_KEY`、`CLERK_SECRET_KEY` 均无 `NEXT_PUBLIC_` 前缀。

## 6. 已知缺口

| 缺口 | 影响 | 追踪 |
|---|---|---|
| 限流基于进程内存 | Serverless 多实例下不共享，形同虚设 | [ADR 0004](../adr/0004-内存滑动窗口限流的适用边界.md)、[限流与可观测性收口](../roadmap/限流与可观测性收口.md) |
| `/api/debug` 无鉴权 | 对外暴露 Supabase 地址与 key 前缀/长度 | [验证状态与发布门禁](../quality/验证状态与发布门禁.md) |
| 建表 SQL 未入库 | 新环境只能用文档口述重建 | 同上 |
| 环境变量校验只告警 | 多数缺失不阻断构建，问题推迟到运行期 | [配置与请求防护架构](配置与请求防护架构.md) |
| 首字节超时阈值未登记 | `AI_FIRST_BYTE_TIMEOUT_MS` 不在 `.env.example` 与部署文档中 | 同上 |
| 代码高亮主题不跟随手动深色切换 | 手动切换后代码块主题可能与页面不一致 | [流式渲染与 UI 架构](流式渲染与UI架构.md) |
| 无 API 集成测试与前端测试 | 主链路回归依赖手工 | [测试与持续集成路线](../roadmap/测试与持续集成路线.md) |
| 无结构化日志与错误上报 | 线上问题缺可检索证据 | [限流与可观测性收口](../roadmap/限流与可观测性收口.md) |
| 文档与代码存在历史不一致 | README/学习日志提到 Next.js 15、50ms 节流、缺失即构建失败，与实际不符 | 见[知识库维护规范](../知识库维护规范.md)第 5 节 |
