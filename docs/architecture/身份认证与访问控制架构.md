# 身份认证与访问控制架构

> 最后核对：2026-10-13
>
> 身份由 Clerk 提供，访问控制由服务端逐请求显式校验承担。数据层细节见[数据模型与持久化架构](数据模型与持久化架构.md)。

## 1. 认证链路

```
浏览器
  → ClerkProvider（app/layout.tsx）注入前端 SDK
  → 未登录：app/page.tsx 渲染登录门（SignInButton mode="modal"）
  → 登录后：useUser() 提供 isSignedIn / user
  → 每个受保护请求由 proxy.ts 走 clerkMiddleware 校验会话
  → Route Handler 内 auth() 取 userId，作为后续所有查询的隔离键
```

- `proxy.ts` 使用 `clerkMiddleware()`，并排除 `_next` 与静态资源，覆盖页面与 `/api` 路由。
- Next.js 16 已用 `proxy.ts` 取代 `middleware.ts`；文件中保留了 `config.matcher`，作用等价于原 middleware 匹配规则。
- 客户端与服务的凭据来自同一 Clerk 实例：`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`（前端）与 `CLERK_SECRET_KEY`（服务端）必须属于同一环境。

## 2. 访问控制矩阵

| 资源 | 未登录 | 已登录（本人） | 已登录（他人） |
|---|---|---|---|
| 聊天页面 | 仅登录门 | 可进入 | 同左 |
| `POST /api/chat` | 401 | 200 / 400 / 429 | 无法指定他人会话：归属校验失败 |
| `GET /api/sessions` | 401 | 仅返回本人会话 | — |
| `GET /api/sessions/[id]/messages` | 401 | 200 | 403 |
| `DELETE /api/sessions/[id]` | 401 | 200 | 403 |
| `GET /api/debug` | **200（无鉴权）** | 200 | — |

`/api/debug` 是唯一未做鉴权的路由，属于待收口项，见[验证状态与发布门禁](../quality/验证状态与发布门禁.md)。

## 3. 会话归属校验的三种写法

代码中存在三种等价但形式不同的校验，理解差异有助于避免漏改：

| 位置 | 写法 | 失败返回 |
|---|---|---|
| `app/api/chat/route.ts#resolveSession` | `select("id").eq("id", sid).eq("user_id", userId).single()` | 抛错 → 500（信息为「会话不存在或无权访问」） |
| `app/api/sessions/[id]/messages/route.ts` | 先 `select("user_id").eq("id", sid).single()`，再在应用层比对 `session.user_id !== userId` | 404（会话不存在）/ 403（无权限） |
| `app/api/sessions/[id]/route.ts` | `select("id").eq("id", sid).eq("user_id", userId).maybeSingle()` | 403（会话不存在或无权限） |

**注意**：`resolveSession` 的失败分支发生在 `try` 内且未映射状态码，最终落到 500 与 `{ "error": "服务器内部错误" }`，语义上更接近 403/404。

## 4. 密钥与凭据边界

| 凭据 | 存放位置 | 可见性 |
|---|---|---|
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | 前端构建内联 | 公开 |
| `CLERK_SECRET_KEY` | 仅服务端 | 保密 |
| `SUPABASE_SERVICE_ROLE_KEY` | 仅服务端（`lib/supabase.ts`） | 保密，绕过 RLS |
| `NEXT_PUBLIC_SUPABASE_URL` / `_ANON_KEY` | 前端构建内联 | 公开（当前前端未直接使用 Supabase SDK） |
| `SILICONFLOW_API_KEY` | 仅服务端（`lib/ai-service.ts`） | 保密 |

服务端密钥不下发的机制是命名前缀：只有 `NEXT_PUBLIC_` 开头的变量才会被 Next.js 内联进客户端包，其余仅在 Node 运行时可见。

## 5. 已知缺口

| 缺口 | 影响 | 追踪 |
|---|---|---|
| `/api/debug` 无鉴权 | 任何人可读取 Supabase 地址与 anon key 前缀/长度 | 发布门禁 P0 |
| 无会话级速率隔离 | 单个 userId 触发限流不影响他人，但无全局配额 | [限流与可观测性收口](../roadmap/限流与可观测性收口.md) |
| 无账号注销与数据删除入口 | 用户无法自助清除自己的全部数据 | 未排期 |
| 无管理员与审计能力 | 无法排查「谁在何时访问了什么」 | 未排期 |
| 无 CSRF 显式防护 | 依赖 Clerk Cookie 的 SameSite 默认策略 | 未验证，需补测试 |
