# ADR 0002：SSE 流式响应协议

- **状态**：已接受
- **日期**：项目早期
- **影响范围**：`lib/sse-response.ts`、`lib/stream-processor.ts`、`app/api/chat/route.ts`、`hooks/useChatStream.ts`

## 背景

上游模型以 SSE 逐 token 返回内容，需要把这份流稳定地转发到浏览器并增量渲染。可选方案：

1. 非流式：服务端等模型输出完成，再一次返回完整 JSON；
2. 服务端→浏览器用 SSE，载荷直接复用上游原始格式；
3. 服务端→浏览器用 SSE，但定义自己的精简载荷；
4. 服务端→浏览器用 WebSocket。

约束：需在 Vercel Serverless 上运行、需能中途取消、需处理 TCP 分包导致的中文截断。

## 决策

采用**方案 3**：

- 传输沿用 `text/event-stream`，响应头固定包含 `Content-Type`、`Cache-Control: no-cache, no-transform`、`Connection: keep-alive`、`X-Accel-Buffering: no`、`Content-Encoding: identity`；
- 服务端不转发上游原始 chunk，而是由 `StreamProcessor` 解析出 `choices[0].delta.content`，重新封装为精简载荷：

```
data: {"token":"<增量文本>","sessionId":"<uuid>"}
```

- 解析按行进行，跨 chunk 的不完整行保留在 buffer 中，等下一次读取再拼接（防止 UTF-8 多字节字符被切断产生乱码）；
- 前端记录 `sessionId` 的首个出现，用于在「新建会话」场景回填当前会话 id。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 方案 1 非流式 | 长回答等待时间不可接受，TTFB 与体感严重劣化 |
| 方案 2 直接复用上游格式 | 把上游 `choices/delta` 结构泄漏到前端，切换模型供应商会连带改前端 |
| 方案 4 WebSocket | Vercel Serverless 不原生支持，需引入额外托管，成本远超收益 |

## 后果

**正面**

- 前端只依赖极小的载荷契约，更换模型供应商不影响前端；
- 逐行解析天然适配 SSE 规范，实现简单、可读性高；
- 精简载荷更小，减少传输开销。

**负面**

- 多一层解析与再编码，服务端 CPU 与代码复杂度上升；
- 自定义协议需要自行维护错误与结束语义，`[DONE]` 等标准约定只能「兼容而不使用」；
- 中断事件的载荷未带 `sessionId`，与正常事件不一致（待收口）。

## 失效条件

- 上游不再提供 SSE 或改为非 OpenAI 兼容结构；
- 需要传输非文本内容（如工具调用中间态、多模态片段）时，精简载荷需要扩展设计。
