# ADR 0003：服务端密钥隔离与密钥边界

- **状态**：已接受
- **日期**：项目早期
- **影响范围**：`lib/supabase.ts`、`lib/ai-service.ts`、`.env.example`、`.gitignore`、Vercel 环境变量

## 背景

项目同时持有三类高权限凭据：Supabase service role key（可绕过 RLS 读写全库）、Clerk secret key、上游模型 API key。若任何一个被内联进前端包，攻击者即可无限调用模型或读取他人数据。

Next.js 的变量可见性由命名前缀决定：只有 `NEXT_PUBLIC_` 开头的变量会在构建时内联到客户端。

## 决策

1. **按最小可见性分配前缀**：只有真正需要在前端使用的匿名级配置才加 `NEXT_PUBLIC_`（Supabase URL / anon key、Clerk publishable key、`NEXT_PUBLIC_APP_URL`）。
2. **高权限凭据只存在于服务端**：`SUPABASE_SERVICE_ROLE_KEY`、`CLERK_SECRET_KEY`、`SILICONFLOW_API_KEY` 均不加前缀，只在 `lib/` 中被读取。
3. **单点持有**：数据库凭据只在 `lib/supabase.ts` 读取一次并导出单例，模型 Key 只在 `lib/ai-service.ts` 拼接请求头。
4. **本地与线上分离**：真实值只存在于本地 `.env.local` 与 Vercel 环境变量；仓库只保留 `.env.example` 占位符，`.gitignore` 忽略 `.env*` 并显式保留 `.env.example`。
5. **不把凭据交给工具**：密钥不粘贴进 AI 对话，改动后复查 `.gitignore` 与提交历史。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 前端直连 Supabase（用 anon key + RLS） | 历史表结构下 RLS 无法生效，需大改表结构与策略 |
| 把 Key 存在前端并由后端转发 | 等价于公开 Key |
| 使用 Vercel Edge Config 存密钥 | 仍是服务端注入，与当前方案等价但增加复杂度 |

## 后果

**正面**

- 前端包内不含任何高权限凭据，泄露面最小；
- 凭据改动只需改一处导出点；
- 变量命名自带语义，评审时一眼可辨可见性。

**负面**

- 无法在客户端使用 Supabase SDK 的实时订阅等能力（当前未使用，无实际损失）；
- 变量缺失只能通过运行时告警发现（大多数变量），需要额外的检查清单兜底。

## 失效条件

- 引入需要在浏览器中使用高权限能力的功能（如客户端实时订阅 + RLS）时，必须同时改造数据层鉴权模型；
- 引入多环境（staging / prod）分离部署时，需要额外约定各环境变量的来源与命名。
