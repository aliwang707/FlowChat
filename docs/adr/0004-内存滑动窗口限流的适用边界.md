# ADR 0004：内存滑动窗口限流的适用边界

- **状态**：已接受
- **日期**：项目早期
- **影响范围**：`lib/rate-limit.ts`、`app/api/chat/route.ts`

## 背景

模型调用按 token 计费，一旦被脚本刷接口会直接产生费用。需要在 `POST /api/chat` 上加入成本保护。

可选方案：

1. 不限制；
2. 进程内存滑动窗口（`Map<userId, {count, resetTime}>`）；
3. 外部共享存储（Redis / Upstash / Vercel KV）；
4. 平台级防护（Vercel WAF / rate limit 中间件）。

## 决策

采用**方案 2**，并把它的边界写进文档而不是假装它是生产级防护：

- 窗口 60 000 ms，上限 20 次，键为 Clerk `userId`；
- 每 5 分钟定时清理过期记录，防止单进程内存无限增长；
- 仅覆盖 `POST /api/chat`；
- 明确记录：Serverless 多实例下 `Map` 不共享，实际放行量约为「实例数 × 20」，仅适合本地开发与单实例演示。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 方案 1 不限制 | 模型 Key 可被刷爆，风险不可接受 |
| 方案 3 外部共享存储 | 需要额外服务与网络往返，对当前单实例演示形态收益不足，留作路线 |
| 方案 4 平台级防护 | 依赖托管平台能力与计划等级，通用性差，不能替代应用层校验 |

## 后果

**正面**

- 零外部依赖，本地开发与单实例部署即时生效；
- 实现 20 行左右，易读易改；
- 边界被显式记录，避免误以为是生产级防护。

**负面**

- 多实例部署下限流基本失效；
- 进程回收或冷启动会重置计数，可通过「打散实例」绕过；
- 未覆盖会话读/删接口，无全局配额概念。

## 失效条件

出现以下任一情况时必须替换为方案 3：

- 线上实例数持续 > 1；
- 出现真实超额调用或异常流量；
- 需要按用户等级分配差异化配额。
