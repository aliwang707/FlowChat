# ADR 0001：单仓 Next.js 全栈与 BFF 边界

- **状态**：已接受
- **日期**：项目早期
- **影响范围**：`app/`、`lib/`、`hooks/`、部署形态

## 背景

FlowChat 需要同时处理流式对话、用户身份、数据持久化和密钥保护。可选的形态有三类：

1. 前端 SPA + 独立后端服务（跨仓库或跨进程）；
2. 单仓 Next.js 全栈，用 Route Handler 充当 BFF；
3. 纯前端直连（前端直接用 Supabase SDK 与上游模型）。

约束条件：个人项目、单人维护、无独立运维预算、必须防止模型 Key 与 service role key 泄露。

## 决策

采用**方案 2：单体 Next.js（App Router）全栈应用**，把服务端能力集中在一个仓库、一次构建、一个部署单元中：

- 所有敏感操作（鉴权、限流、模型调用、数据写入）只发生在 `app/api/**/route.ts`；
- 浏览器不持有任何高权限凭据，也不直接访问数据库；
- `lib/` 作为服务端领域层，供路由复用，不被客户端组件 import。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 方案 1 独立后端 | 需要额外部署、跨域配置、鉴权双写；对单人项目收益不足 |
| 方案 3 纯前端直连 | service role key 必须下发前端才可写入，等于公开数据库高权限；密钥必被泄露 |
| 使用 Supabase 原生 RLS 做隔离 | 历史表结构中 `user_id` 为 `text`，与 `auth.uid()` 的 `uuid` 不匹配，策略无法直接生效 |

## 后果

**正面**

- 密钥只在 Node 运行时可见，前端包中不含高权限凭据；
- 鉴权、校验、限流、落库集中在一处，便于审计与统一改动；
- 一次 `git push` 即完成全栈部署，无跨服务版本漂移问题。

**负面**

- 前端与后端共享同一个构建产物，任何服务端依赖误引入客户端都会增大包体甚至直接报错；
- Serverless 形态带来函数超时、冷启动、内存状态不共享等约束（如限流失效）；
- 无法按前后端分别扩缩容。

## 失效条件

满足任一条件时，应重新评估本决策：

- 需要长连接、WebSocket 或超过平台函数时长上限的任务；
- 需要独立扩缩容后端或引入队列、定时任务；
- 团队规模扩大，前后端需要独立发布节奏。
