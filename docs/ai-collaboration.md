# AI 辅助开发说明：如何用 AI 加速开发但不盲从

## 协作定位

本项目在开发过程中深度使用了 **AI IDE（Trae / Cursor / GitHub Copilot） + Chat 类工具（Claude / 元宝）** 作为编程搭档。AI 扮演“结对程序员 + 代码审查者”的角色，我负责“需求拆解 + 架构决策 + 质量把关”。

---

## 一、核心协作模式

### 1. 教练式引导而非直接给代码

AI 不直接输出完整代码，而是通过**提问**引导我思考每一步的设计决策：

- **用生活化比喻建立心智模型**：用“邮差送信”区分 Request / Response；用“快递标签”理解前后端数据契约；用“吸管喝奶茶”理解 `TransformStream` 的流式过滤器本质。
- **故意留白**：在代码框架中留出 `???` 让我自己查文档填空，而不是直接给出答案。
- **倒逼思考**：“如果这个接口上线，哪里会挂？如果有人写脚本每秒调你 100 次，你的额度能撑多久？”

### 2. 报错驱动开发与精准提问

- **提供完整上下文**：向 AI 提问时，我会提供文件路径、终端报错日志、浏览器 Network 截图，以及我已经尝试过的方案。避免“我这里报错了怎么办”这种无上下文提问。
- **追问“为什么”**：不仅问怎么修，更要问为什么会发生（如 `PGRST204` 类型不匹配）。
- **上下文裁剪**：长对话中 AI 容易丢失早期约束，我会通过新建会话并粘贴关键代码片段来保持聚焦。

### 3. 分层验证，不盲信输出

AI 给出的代码**必须理解后再采用**。遇 Bug 时，我的定位思路是：

1. 先看日志 / 报错定位到具体文件和行号
2. 用最小复现验证假设
3. 区分「代码错误」与「环境问题」

每次修复后，我都会执行 `npm run build` 与人工测试来验证改动，绝不将未验证的代码推送到远程仓库。


### 4. AI IDE 工作流：从“对话式问答”升级到“代码库级协作” 
我不只把 AI 当网页对话框，而是将其作为 IDE 的一部分。我使用 Trae 和通义灵码作为主力开发环境，通过 `@Codebase` 功能让 AI 理解整个项目上下文。在遇到复杂代码逻辑时，我不再手工搜索或复制片段，而是直接向 AI 提出精确的问题，并让它输出结构化分析或测试代码。每次 AI 的输出，我都会在本地通过 `npm run build` 和单元测试进行验证。

## 二、典型协作案例

### 案例一：产品决策 —— 取消生成的数据一致性

- **AI 初期方案**：取消生成时，直接删除用户消息，实现完全回滚。
- **我的独立思考**：我对照了主流产品（ChatGPT、Kimi），发现它们都保留用户消息，以便用户继续追问。
- **最终决策**：我否决了 AI 的方案，决定保留用户消息，不保存空的 AI 回复；若 AI 已生成部分内容，则保存并标记 `[用户已中断]`，过滤空消息避免污染后续上下文。

这体现了我结合产品场景做判断，而非盲目照搬 AI 方案。

### 案例二：流式输出的“三轮攻坚”

在排查流式输出问题时，我和 AI 经历了三个不同维度的迭代排查：

1. **编码层**：中文乱码、内容截断。怀疑 UTF-8 解码 → 引入 `TextDecoderStream` 处理多字节。
2. **渲染层**：输出重复、停不下来。怀疑渲染频率 → 引入 `lodash.throttle` 节流。
3. **数据层**：代码混入中文。怀疑后端数据污染 → 查看 Network 面板原始响应，后端防御空 `choices` 并移除 `stream_options`。

**收获**：如果只停留在第一轮，永远修不好。分层定位问题才是解决复杂 Bug 的核心能力。

### 案例三：工程健壮性与安全审计

- **环境变量防呆**：AI 建议使用占位符兜底，我改为在启动时用 Zod 校验，缺失时直接构建失败，避免线上静默连到假地址。
- **竞态条件拦截**：快速切换会话导致旧数据覆盖新数据。我引入了 `requestId` 拦截过期请求，并使用 `messagesRef` 解决 React 闭包陷阱（Stale Closure）。
- **安全红线**：严格区分 `NEXT_PUBLIC_` 变量和私密 Key。API Key、Service Role Key 等敏感信息绝不暴露到客户端，绝不直接粘贴给 AI，并在每次修改后审查 `.gitignore` 和代码历史防泄漏。

### 案例四：AI IDE 实战 —— 用 Trae 攻克核心逻辑与测试 (新增，重点展示)
我把 FlowChat 项目导入 Trae 后，利用其代码库索引能力和 Agent 模式，完成了以下三项高价值的协作实战：

**场景一：追问底层原理 —— SSE 的多字节截断处理**
- **我的提问**：“`useChatStream.ts` 里 SSE 的 buffer 拼接逻辑是怎么处理中文截断的？”
- **AI 的反馈**：Trae 通过读取整个项目，精确找到了 `TextDecoder` 的调用位置，并用图解方式解释了 UTF-8 中文字符（占 3 字节）被 TCP 分包切断时，如何通过 `buffer += decoder.decode(chunk, { stream: true })` 来暂存不完整字符。
- **我的验证**：我没有只看了答案就结束。我在本地故意模拟了慢速网络（Chrome Network Throttling），观察 `buffer` 的长度变化，确认中文没有变成 `��`。
- **收获**：我不仅知道了“怎么写”，更知道了“为什么这么写”，并把这条路径更新到了 `troubleshooting.md` 中。

**场景二：补全工程化短板 —— 为 Zod Schema 生成单元测试**
- **我的提问**：“帮我给 `ChatRequestSchema` 写一个 Vitest 单元测试，覆盖非法输入。”
- **AI 的反馈**：Trae 生成了初版测试代码，覆盖了 `messages` 为空、`role` 非法、`content` 超长等场景。
- **我的审查与修正**：我审查后，发现 AI 漏掉了“完全缺失 `messages` 字段”和“`content` 为非字符串”这两个边界情况。我手动补上了 `it('should fail when messages is missing', ...)` 和 `it('should fail when content is not a string', ...)`。
- **最终产出**：`npm run test` 全绿，单元测试覆盖率大幅提升，并被我配置进了 GitHub Actions 的 CI 流水线。

**场景三：梳理并发逻辑 —— 让 AI 帮我画出竞态拦截的数据流**
- **我的提问**：“快速切换会话时，`requestId` 是如何拦截过期请求的？帮我画出数据流。”
- **AI 的反馈**：Trae 输出了一个 Mermaid 时序图，清晰标注了 `requestId` 的产生、传递和比对逻辑。
- **我的理解**：我对照时序图，在代码里找到了对应的 `if (currentRequestId !== latestRequestId) return;` 拦截逻辑。
- **收获**：我把这张图放进了 `docs/architecture.md`，让我对 React 的并发状态管理有了全局视角，面试时可以直接拿着图讲。

## 三、我的角色 vs. AI 的角色

| 环节 | AI 负责 | 我负责 |
| --- | --- | --- |
| 需求拆解 | 生成功能清单、目录结构草稿 | 判断优先级，裁剪范围，定义 API 契约 |
| 架构设计 | 提供多种方案对比（如流式 vs 非流式） | 结合业务做技术选型，决定最终落地架构 |
| 代码生成 | 生成组件骨架、类型定义、样板逻辑 | 审查类型、边界、安全性，手动补充 `try-catch` 兜底 |
| 调试排错 | 分析终端日志、提供修复方向 | 复现问题，看 Runtime Logs，验证修复并观察线上表现 |
| 优化重构 | 指出潜在隐患（如闭包、竞态）、给出通用建议 | 理解原理后手动修改并测试，评估性能与可维护性 |
| 文档整理 | 辅助整理结构、生成注释 | 校正事实，补充真实经历与工程细节 |

## 四、AI 协作的边界与反思

### 1. AI 的局限性

- **不擅长架构决策**：AI 可以提供参考方案，但业务可行性必须由人判断。
- **边界条件容易出错**：AI 生成的代码在极端情况下（不完整 JSON、网络中断、`.at(-1)` 返回 `undefined`）会出问题，必须人工补充边界处理。
- **存在 AI 幻觉**：如误用不存在的代码库，或混淆 `pipeTo()` 与 `pipeThrough()`，需要通过运行和静态分析工具来纠偏。
- **不感知线上环境**：AI 对 Vercel 的 Serverless 环境、数据库连接池、真实网络请求不敏感，必须依赖人工排查。

### 2. 反思与成长

- **前期进度慢**：一开始我直接要完整代码，后来意识到“自己写出来的东西才是自己的，抄一遍顶多看个热闹”。
- **形成学习策略**：
  - 语法 / API 用法 → 自己查 MDN、TypeScript 手册、Next.js 文档。
  - 设计决策 / 架构理解 → 找 AI 讨论，让它反问我以验证理解。
  - 调试定位 → AI 给方向提示，自己顺着查。
  - 工程化取舍 → AI 给选项和权衡，自己决策。
- **新习惯**：写代码前先在注释里把流程走一遍（拿到请求 → 校验 → 存库 → 调用 AI → 流式转发 → 存回复 → 返回状态码），先有“路线图”，再填“代码”。

---

## 五、总结

AI 生成，我审查；AI 建议，我验证；AI 排错，我定位。
AI 是加速器，不是替代品。我不仅会用 Chat 类工具讨论思路，更具备使用 AI IDE（Trae）进行代码库级协作、测试生成与架构梳理的现代工程能力。我对自己提交的每一行代码负责。
